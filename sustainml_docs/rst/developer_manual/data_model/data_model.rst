.. _data_model:

SustainML Framework Data Model
==============================

The following data structure definitions use the `Interface Definition Language specification <https://www.omg.org/spec/IDL/4.2/About-IDL>`_.
All of them are defined in ``sustainml_cpp/include/sustainml_cpp/idl/typesImpl.idl``, and the interfaces of the
configuration service in ``sustainml_cpp/include/sustainml_cpp/idl/SustainMLService.idl``.

The IDL structures have the ``Impl`` suffix, which is also the name of their DDS types.
The C++ API of ``sustainml_cpp`` wraps each of them in a class of the ``types`` namespace without the suffix (for
instance, ``types::NodeStatus`` wraps ``NodeStatusImpl``), and the Python API uses the same classes through the
``sustainml_swig`` bindings.

Every data structure of a task has a ``task_id`` key, and most of them an ``extra_data`` field.
In the current nodes, ``extra_data`` always carries a JSON object encoded in UTF-8, through which the nodes pass each
other the data that has no field of its own.
The keys used by each node are listed in the sections below.

Every node in the *SustainML Framework* must continuously report its status to the :ref:`orchestrator`, with the
``NodeStatusImpl`` data structure.

.. _task_id_type:

Task Id Type
------------

The ``TaskIdImpl`` data structure identifies a task, that is, an iteration of a problem defined by the user:

* ``problem_id``: The identifier of the problem, generated by the :ref:`orchestrator` for each new problem
  (starting from ``1``).
* ``iteration_id``: The identifier of the iteration of that problem (starting from ``1``).

.. code-block:: omg-idl

    struct TaskIdImpl
    {
        unsigned long problem_id;
        unsigned long iteration_id;
    };

.. _node_status_type:

Node Status Type
----------------

Each node publishes its ``NodeStatusImpl`` in the ``/sustainml/status`` topic when it starts, and before and after
each task.
It has the following fields:

* ``node_status``: The status of the node.
  A node is ``NODE_INITIALIZING`` and then ``NODE_IDLE`` when it starts, ``NODE_RUNNING`` while it processes a task,
  and then ``NODE_IDLE`` again or ``NODE_ERROR`` if the task failed.
  The orchestrator sets ``NODE_INACTIVE`` when the node leaves the DDS domain.
* ``task_status``: The status of the task.
* ``error_code``: The error code.
* ``error_description``: A description of the error.
* ``node_name``: The name of the node.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    enum Status {
        NODE_INACTIVE,
        NODE_ERROR,
        NODE_IDLE,
        NODE_INITIALIZING,
        NODE_RUNNING,
        NODE_TERMINATING
    };

    enum TaskStatus {
        TASK_WAITING,
        TASK_ERROR,
        TASK_RUNNING,
        TASK_SUCCEEDED
    };

    enum ErrorCode {
        NO_ERROR,
        INTERNAL_ERROR
    };

    struct NodeStatusImpl
    {
        Status node_status;
        TaskStatus task_status;
        ErrorCode error_code;
        string error_description;
        @key string node_name;
        @key TaskIdImpl task_id;
    };

.. _node_control_type:

Node Control Type
-----------------

The ``NodeControlImpl`` data structure models the commands to manage the lifecycle of nodes and tasks, published in
the ``/sustainml/control`` topic.
It is internally used in the communication library.
Every node subscribes to this topic, but the nodes only log the commands they receive, and the framework does not
send any (see :ref:`orchestrator`).

.. code-block:: omg-idl

    enum CmdNode {
        NO_CMD_NODE,
        START_NODE,
        STOP_NODE,
        RESET_NODE,
        TERMINATE_NODE
    };

    enum CmdTask {
        NO_CMD_TASK,
        STOP_TASK,
        RESET_TASK,
        PREEMPT_TASK,
        TERMINATE_TASK
    };

    struct NodeControlImpl
    {
        CmdNode cmd_node;
        CmdTask cmd_task;
        string target_node;
        @key string source_node;
        @key TaskIdImpl task_id;
    };

.. _user_input_type:

User Input Type
---------------

The ``UserInputImpl`` data structure carries the input from the user when describing a new task (Machine Learning
problem), which the :ref:`orchestrator` publishes in the ``/sustainml/user_input`` topic.
It has the following fields:

* ``modality``: The modality of the input data.
  The Front-End no longer sends it, so it is empty.
* ``problem_short_description``: The description of the problem, written by the user.
* ``problem_definition``: The type of problem to solve, for instance classification, regression or clustering.
* ``inputs``: The words of the description of the input data.
* ``outputs``: The words of the description of the output data.
* ``minimum_samples``: The minimum number of samples (``0`` when not specified).
* ``maximum_samples``: The maximum number of samples (``0`` when not specified).
* ``optimize_carbon_footprint_manual``: Whether the user reiterates the problem by hand (the **Reiterate** button of
  the GUI) to get models with a lower carbon footprint, so that the models already tried are not proposed again.
* ``previous_iteration``: ``0`` for a new problem, or the iteration of the problem from which this one is a
  reiteration.
* ``optimize_carbon_footprint_auto``: Whether the framework reiterates the problem on its own until a model meets the
  desired carbon footprint and the maximum memory footprint.
* ``desired_carbon_footprint``: The desired carbon footprint per inference, in ``gCO2e`` (``0`` for no target).
  It is sent with or without an optimization: the GUI ranks the results against it in any case, and the automatic
  optimization also searches again when a model misses it.
* ``geo_location_continent``: The continent where the ML model is going to run.
* ``geo_location_region``: The country where the ML model is going to run, as an ISO 3166-1 alpha-2 code, used to get
  the carbon intensity of its electricity grid.
* ``extra_data``: The JSON object described below.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct UserInputImpl
    {
        string modality;
        string problem_short_description;
        string problem_definition;
        sequence<string> inputs;
        sequence<string> outputs;
        unsigned long minimum_samples;
        unsigned long maximum_samples;
        boolean optimize_carbon_footprint_manual;
        long previous_iteration;
        boolean optimize_carbon_footprint_auto;
        double desired_carbon_footprint;
        string geo_location_continent;
        string geo_location_region;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

The ``extra_data`` of the user input is filled by the Front-End, the Back-End and the :ref:`orchestrator` with the
following keys:

* ``hardware_required``: The hardware selected by the user (``PIM_AI_1chip`` by default).
* ``max_memory_footprint``: The maximum memory footprint of the model, in MB (``0`` means no limit).
* ``goal``: The ML goal chosen by the user, if any.
* ``model_selected``: The model chosen by the user, if any.
* ``type`` and ``model_family``: The family of models (for instance, ``Transformers`` or ``CNNs``).
* ``num_outputs``: The number of models the user asked for.
* ``model_restrains``: The models that must not be proposed, because they were already tried.
* ``previous_problem_id``: The problem of which this task is a reiteration.
* ``auto_attempt``: The attempt of the automatic carbon footprint optimization.
* ``hf_token``: The Hugging Face token of the Back-End.
* ``hf_analyze``: Whether the task evaluates a model of a Hugging Face search.
* ``dataset_metadata_description``, ``dataset_metadata_topic``, ``dataset_metadata_profile``,
  ``dataset_metadata_keywords`` and ``dataset_metadata_applications``: The description of the dataset of the user, if
  one was described.

.. _mlmodelmetadata_type:

ML Model Metadata Type
----------------------

The ``MLModelMetadataImpl`` data structure represents the output from the :ref:`mlmodelmetadata_node`.
It has the following fields:

* ``keywords``: A sequence of keywords of the problem.
  The current node does not fill it.
* ``ml_model_metadata``: The ML goal of the problem, as a single element: the goal chosen by the user, or the one the
  node infers from the problem description.
  It is empty when the user chose a model.
* ``extra_data``: A JSON object with ``problem_short_description``, and the ``model_restrains``, ``model_selected``,
  ``type`` and ``hardware_required`` of the user input when they are set.
  For YOLO models on the Axelera board, it also has ``yolo_preferences``, the requirements read from the problem
  description.
  When no goal can be found, it is ``{"error": <message>}``.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct MLModelMetadataImpl
    {
        sequence<string> keywords;
        sequence<string> ml_model_metadata;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _apprequirements_type:

Application Requirements Type
-----------------------------

The ``AppRequirementsImpl`` data structure represents the output from the :ref:`appreqs_node` and has the following
fields:

* ``app_requirements``: A sequence of application-level requirements, modeled as a sequence of strings, to be
  considered in the selection of the machine learning model.
  The current node only fills it with placeholder values.
* ``extra_data``: A sequence of raw extra data for out-of-scope use cases.
  The current node does not fill it.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct AppRequirementsImpl
    {
        sequence<string> app_requirements;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _hardware_constraints_type:

Hardware Constraints Type
-------------------------

The ``HWConstraintsImpl`` data structure represents the constraints that the user can define when describing the
problem.
It is the output from the :ref:`hwconstraints_node`.

* ``max_memory_footprint``: The maximum memory footprint allowed for the ML model, in MB (``0`` means no limit).
* ``hardware_required``: The hardware selected by the user, as a single element.
* ``extra_data``: A copy of the ``extra_data`` of the user input.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct HWConstraintsImpl
    {
        unsigned long max_memory_footprint;
        sequence<string> hardware_required;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _mlmodel_type:

ML Model Type
-------------

The ``MLModelImpl`` data structure represents the output from the :ref:`mlmodelprovider_node`.
It has the following fields:

* ``model_path``: The path to the ONNX file of the model, for the U-Net models, or empty for the other ones.
* ``model``: The name of the model (for instance, a Hugging Face model id), or ``NO_MODEL`` when no model was found.
* ``raw_model``: A sequence of bytes with the raw model, in case of remote approach.
* ``model_properties_path``: A string containing the path to the properties of the model.
* ``model_properties``: A string with the model properties, in case of remote approach.
* ``input_batch``: A sequence of serialized input batches for the model.
* ``target_latency``: The target latency of the model.
* ``extra_data``: ``{"unsupported_models": [...]}``, or ``{"error_code": "NO_MODEL", "error": <message>}`` when no
  model was found.
* ``task_id``: The identifier of the task.

The current node only fills ``model``, ``model_path`` and ``extra_data``.

.. code-block:: omg-idl

    struct MLModelImpl
    {
        string model_path;
        string model;
        sequence<octet> raw_model;
        string model_properties_path;
        string model_properties;
        sequence<string> input_batch;
        double target_latency;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _hardware_resource_type:

Hardware Resource Type
----------------------

The :ref:`hwprovider_node` estimates the resources the ML model needs on the hardware selected by the user.
The ``HWResourceImpl`` data structure holds that information in the following fields:

* ``hw_description``: The name of the hardware.
* ``power_consumption``: The power consumption of the model on the hardware, in ``W``.
* ``latency``: The latency of one inference of the model on the hardware, in hours.
* ``memory_footprint_of_ml_model``: The memory footprint of the model on the hardware, in MB.
* ``max_hw_memory_footprint``: The maximum memory footprint set by the user, in MB (``0`` means no limit).
* ``extra_data``: DFKI's prediction for the FPGA, ``{"axelera": ..., "accuracy": ...}`` with the
  measured resources and the accuracy of the YOLO models on the Axelera board, nothing for the simulator
  architectures, or an object with an ``error`` key when the resources could not be computed.
* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct HWResourceImpl
    {
        string hw_description;
        double power_consumption;
        double latency;
        double memory_footprint_of_ml_model;
        double max_hw_memory_footprint;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _carbonfootprint_type:

Carbon Footprint Type
---------------------

The output from the :ref:`carbontracker_node` is modeled by the ``CO2FootprintImpl`` data structure, which has
the following fields:

* ``carbon_footprint``: The carbon footprint of one inference, in ``gCO2e``.
* ``energy_consumption``: The energy consumption of one inference, in ``kWh``.
* ``carbon_intensity``: The carbon intensity of the electricity grid used, in ``gCO2/kWh``.
* ``extra_data``: A JSON object with:

  * ``num_outputs``: The number of models still to propose for the problem, including this one.
  * ``model_restrains``: This model and the models already tried.
  * ``grid_ci_source``: The country and year of the carbon intensity used, and how the country was chosen.
  * ``mode``: How the carbon footprint was obtained: ``hw_simulated``, ``onnx_hw_only``, ``axelera_measured``,
    ``tracker``, ``no_model`` or ``error``.
  * ``auto_reiterate``: Whether the :ref:`orchestrator` must try another model (automatic carbon footprint
    optimization).
  * ``error``: The error, when the carbon footprint could not be computed.

* ``task_id``: The identifier of the task.

.. code-block:: omg-idl

    struct CO2FootprintImpl
    {
        double carbon_footprint;
        double energy_consumption;
        double carbon_intensity;
        sequence<octet> extra_data;
        @key TaskIdImpl task_id;
    };

.. _service_types:

Service Types
-------------

``RequestTypeImpl`` and ``ResponseTypeImpl`` are the data structures used by the :ref:`node_config_service`.
They are not sent over DDS as such: the orchestrator and the nodes use them in their APIs, while the RPC carries the
``configuration`` string and returns the encoded reply.

The ``RequestTypeImpl`` structure has the following fields:

* ``node_id``: The identifier of the target node, a value of the ``NodeID`` enum (see :ref:`node_ids`).
* ``transaction_id``: A unique counter internal to the orchestrator.
* ``configuration``: The request string.

The ``ResponseTypeImpl`` structure has the following fields:

* ``node_id``: The identifier of the node, copied from the request.
* ``transaction_id``: The transaction identifier, copied from the request.
* ``success``: Whether the request was successful.
* ``err_code``: The error code of the node, ``NO_ERROR`` or ``INTERNAL_ERROR``.
* ``configuration``: The answer of the node, usually a JSON object encoded as a string.

.. code-block:: omg-idl

    struct RequestTypeImpl
    {
        @key long node_id;
        @key long transaction_id;
        string configuration;
    };

    struct ResponseTypeImpl
    {
        @key long node_id;
        @key long transaction_id;
        boolean success;
        ErrorCode err_code;
        string configuration;
    };

``SustainMLService.idl`` defines the RPC interfaces of the service, one per module node, as shown in
:ref:`node_config_service`.
