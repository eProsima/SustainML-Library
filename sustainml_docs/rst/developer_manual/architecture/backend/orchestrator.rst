The :ref:`orchestrator` of the *SustainML Framework* launches the tasks, gathers the data generated by each of the
:ref:`module_nodes` and acts as the data source for the :ref:`frontend`.

It is made of two layers:

* The C++ ``OrchestratorNode`` class of ``sustainml_cpp``
  (``sustainml_cpp/include/sustainml_cpp/orchestrator/OrchestratorNode.hpp``), which holds all the DDS communication:
  it publishes the user input of each task, receives the output and the status of every node, stores the results and
  sends the configuration requests.
  It reports to the application through an ``OrchestratorNodeHandle``, whose ``on_new_node_output()`` and
  ``on_node_status_change()`` callbacks are called for every new node output and node status.
* The Python ``Orchestrator`` class (``sustainml-wp5/orchestrator_node/orchestrator_node.py``), which wraps the C++ class
  through the SWIG bindings, implements the handle, turns the results into JSON objects, decides the automatic
  reiterations and saves and loads the results into files.

The Python ``Orchestrator`` runs in its own thread inside the Back-End process (``sustainml-wp5/backend_node.py``), whose
Flask server exposes it to the Front-End through the REST API described in :ref:`frontend`.

The Orchestrator Node has the following responsibilities:

Track the nodes and their status
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The orchestrator creates the DDS participant ``ORCHESTRATOR_NODE``.
When it discovers the participant of a module node (the participant names are ``APP_REQUIREMENTS_NODE``,
``CARBON_FOOTPRINT_NODE``, ``HW_CONSTRAINTS_NODE``, ``HW_RESOURCES_NODE``, ``ML_MODEL_METADATA_NODE`` and
``ML_MODEL_NODE``), it creates a proxy of that node, which subscribes to the output topic of the node and to the status
topic, filtered by the name of the node.
When the participant of a node leaves the domain, the orchestrator sets the status of that node to ``INACTIVE``.

Every node publishes its status (see :ref:`node_status_type`) in the ``/sustainml/status`` topic: ``INITIALIZING`` and
then ``IDLE`` when it starts, ``RUNNING`` while it processes a task, and then ``IDLE`` again, or ``ERROR`` if the task
failed.
The Python ``Orchestrator`` keeps the last status received from each node, and the Back-End returns them in its
``/status`` endpoint, as the strings ``INACTIVE``, ``ERROR``, ``IDLE``, ``INITIALIZING``, ``RUNNING`` or
``TERMINATING``.
A node that has not reported any status yet is not listed.
The Front-End considers the framework ready when the six nodes are ``IDLE``.

The orchestrator also has a writer in the ``/sustainml/control`` topic (see :ref:`node_control_type`) and a
``send_control_command()`` method, and every node subscribes to that topic.
However, the nodes only log the commands they receive, and neither the Python ``Orchestrator`` nor the Back-End sends
any: a running task cannot be stopped.

Launch and monitor tasks
^^^^^^^^^^^^^^^^^^^^^^^^

Each run of the pipeline has an associated ``task_id``, made of a ``problem_id`` and an ``iteration_id``
(see :ref:`data_model`).
A ``problem_id`` is generated for each problem the user defines, and an ``iteration_id`` for each iteration of that
problem:
reiterating a problem to get another model for it keeps the ``problem_id`` and increases the ``iteration_id``.

The Back-End passes every user input it receives to ``Orchestrator.send_user_input()``:

* If ``previous_iteration`` is ``0``, it is a new problem: ``OrchestratorNode::prepare_new_task()`` creates the next
  ``problem_id`` (they start at ``1`` and grow by one) with ``iteration_id`` ``1``.
* Otherwise, it is a new iteration of the problem given in the ``previous_problem_id`` key of ``extra_data``:
  ``OrchestratorNode::prepare_new_iteration()`` creates a new ``iteration_id`` for that problem and copies the user
  input of the previous iteration into it.
  The new ``iteration_id`` is the one after ``previous_iteration``, or after the latest task of the session when that
  task belongs to the same problem and is a later iteration.

Then the fields of the request overwrite the user input, ``extra_data`` is completed (see :ref:`user_input_type`) and
``OrchestratorNode::start_task()`` publishes it in the ``/sustainml/user_input`` topic, together with the baselines of
the previous iteration (see :ref:`architecture`).
When the carbon footprint optimization (manual or automatic) is enabled in a reiteration and no model was chosen by
the user, the models already tried in any iteration of the problem are added to ``model_restrains``, so that they are
not proposed again.

For every task, the Python ``Orchestrator`` keeps a flag per node that is set when the output of that node for the task
arrives.
A request for the results of a node waits until that flag is set, so the Back-End answers the result requests of the
Front-End as soon as each node has finished.

The orchestrator also launches the following iterations of a task on its own, when the output of the
:ref:`carbontracker_node` arrives:

* If its ``extra_data`` has ``auto_reiterate`` set to ``true`` (automatic carbon footprint optimization, when the model
  misses the desired carbon footprint or the maximum memory footprint), it sends a new iteration with the models
  already tried in ``model_restrains`` and ``auto_attempt`` increased by one.
  The :ref:`carbontracker_node` stops asking for it after three attempts.
* Otherwise, if the user asked for more than one output model (``num_outputs`` greater than ``1``), it sends a new
  iteration with ``num_outputs`` decreased by one and the models already proposed in ``model_restrains``.

Store the results
^^^^^^^^^^^^^^^^^

All the data of the tasks are kept in memory, in the task database of the C++ ``OrchestratorNode``, indexed by the
``task_id``: a map from each ``problem_id`` to an ordered map from each ``iteration_id`` to the user input and the
outputs of the six nodes for that iteration.
The node proxies store every node output in it as soon as it arrives.

The Python ``Orchestrator`` reads these data through the SWIG bindings and converts them into JSON objects, which the
Back-End returns in its ``/results`` endpoint.
This in-memory data is lost when the Back-End stops: nothing is written to disk automatically.

Save and load the results
^^^^^^^^^^^^^^^^^^^^^^^^^

The results are saved into named save files only when the user asks for it, and can be loaded back later
(``sustainml-wp5/orchestrator_node/persistence.py``).
Each save is an SQLite database file, ``<name>.sqlite3``, in the save directory, which is the first usable directory
of the following:

#. The directory set in the ``SUSTAINML_DB_PATH`` environment variable.
#. ``/opt/sustainml/db``.
#. ``$XDG_DATA_HOME/sustainml``, or ``~/.local/share/sustainml`` when ``XDG_DATA_HOME`` is not set.

The save name keeps only letters, digits, spaces, underscores, hyphens and ``/``; a ``/`` is written in the file name
as the ``∕`` (division slash) character, so that every save is a single file directly under the save directory.

A save file has three tables:

* ``tasks``: one row per task (``problem_id``, ``iteration_id``), with the JSON result of the user input and of each
  node, and a ``status`` that is ``complete`` when the six node results are saved, ``partial`` when only some of them
  are, and ``pending`` when none is.
* ``problems``: the name the user gave to each problem in the Front-End.
* ``hf_state``: the Hugging Face searches and comparisons of the Front-End, as two opaque JSON lists (``searches`` and
  ``comparisons``) that the Back-End stores and returns as they are.

Saving the tasks under an existing name replaces all the tasks of that file, but keeps its Hugging Face history, and
saving one part of the Hugging Face history keeps the tasks and the other part.
Only the node results that have already arrived are saved; the save does not wait for a node that has not finished
yet.

When the tasks of a file are loaded, each saved problem gets a new ``problem_id`` (the iterations keep their
``iteration_id``), so that loaded tasks never collide with the tasks of the session.
Their results are kept in a cache of the Python ``Orchestrator``, with the ``task_id`` inside each result rewritten to
the new one, and returned from there by the ``/results`` endpoint: loaded tasks are not run again.
A node result that was not saved is returned as a message saying so, instead of being waited for.

The endpoints that list, save, load and delete these files are described in :ref:`frontend`.
